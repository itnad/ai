# newai 요구사항 정의

작성일: 2026-11-27 · 버전: 0.1(구현 전)

## 1. 목적

Claude Code는 선택이 필요하거나 환경 제약을 만나면 사람을 무한정 기다린다. 자리를 비우면 작업이 멈춘다.
newai는 **사람이 없어도 멈추지 않고, 합리적으로 판단해서 계속 진행하는 개발 자동화 하네스**다.
되돌리기 어려운 일(push, 배포, 전역 설정 변경, 삭제)은 끝까지 사람이 한다.

## 2. 사용자와 사용 환경

- 사용자: 한 명의 개발자(본인). 주 사용 환경은 Windows PC, 보조로 Linux/macOS.
- 실행 형태: 이 PC에서 도는 백그라운드 서버 + 터미널 화면(`newai`) + 웹 화면(대시보드) + 관리 명령(`harness`).
- 인증: 기본은 이 PC에 로그인된 Claude Code(본인 전용). API 키는 설정으로 바꿀 수 있게 둔다(2026-11-27 사용자 결정).
- 커밋: 구현 단계마다 로컬 커밋, push는 사용자가 한다(2026-11-27 사용자 결정).
- 언어: 모든 화면·보고·문서는 한국어. 사용자가 다른 언어를 명시하면 그것이 우선한다. 한자 금지.

## 3. 용어

| 용어 | 뜻 |
|---|---|
| 작업(job) | 사용자 요청 하나를 처리하는 단위. 큐에 들어가고 상태를 가진다 |
| 결정 카드 | 하네스가 사람 대신 답할 수 있는 질문 하나. 추천안 3개, 점수, 남은 시간을 가진다 |
| 판단 모델 | 결정 카드의 추천안을 점수화하는 별도 Claude 호출. 중립 폴더에서 메모리 없이 돈다 |
| 설치 폴더 | newai 코드가 있는 곳 (`INSTALL_DIR`) |
| 데이터 폴더 | 설정·정책·DB·로그·프로젝트가 있는 곳 (`NEWAI_HOME`) |
| 파이프라인 | 요구사항 → 설계 → 명세 → 구현 → 검증 → 커밋의 단계 묶음 |

## 4. 기능 요구사항

각 항목의 ID는 명세(`spec.md`)와 테스트에서 그대로 쓴다.

### F1. 결정 엔진
- F1.1 AskUserQuestion, 계획 승인(ExitPlanMode), 권한 확인을 모두 가로채 결정 카드로 만든다.
- F1.2 판단 모델이 가점 기준으로 추천안 3개를 점수화한다. 원래 선택지가 4개면 상위 3개, 2개면 2개 + 판단 모델 제안 1개.
- F1.3 대기 시간(20초·1분·5분·10분·20분) 안에 사람이 고르지 않으면 자동 선택 가능한 추천안 중 1순위를 적용한다.
- F1.4 사람은 언제든 고르기, 골라 두기(시간이 끝나면 적용), 직접 입력, 타이머 멈춤/재개를 할 수 있다.
- F1.5 대기 시간은 전역 설정으로 저장되고, 이미 떠 있는 카드에도 즉시 적용된다.
- F1.6 모든 결정은 누가(사람/자동/골라 둔 답/정책) 무엇을 왜 골랐는지 기록된다.

### F2. 안전장치(여러 겹)
- F2.1 push·배포 선택지는 자동 선택 대상에서 뺀다.
- F2.2 PreToolUse 훅으로 위험 명령을 차단한다.
- F2.3 에이전트 실행 환경에 git `pushInsteadOf` 환경 변수를 넣어 스크립트 안의 push까지 막는다.
- F2.4 고위험(대량 삭제, 이력 파괴, DB 파괴, 비밀 파일 접근)은 사람 승인만 받는다.
- F2.5 외부 통신은 대기 시간을 반드시 거친다(즉시 자동 허용 금지).
- F2.6 작업 폴더 밖 수정은 대기 필수. 하네스 자신의 코드·정책 수정은 사람 승인.
- F2.7 정책은 `policy.yaml` 하나로 관리하고, 수정은 사람만 한다.

### F3. 대화형 화면
- F3.1 `newai` 명령은 서버가 없으면 백그라운드로 켜고, 대화하듯 요청을 받는다.
- F3.2 터미널 화면과 웹 화면이 같은 대화를 보여 준다. 웹 화면도 터미널처럼 하단 결정 카드를 키보드로 조작한다.
- F3.3 진행 상황을 실시간으로 표시한다. 터미널 진행 표시는 깜빡이지 않게 한 번에 덮어쓴다.
- F3.4 앞 대화를 이어간다. 창을 닫거나 서버를 재시작해도 유지된다.
- F3.5 작업 중에 다음 요청을 예약할 수 있고, 예약은 서버 큐에 저장된다.
- F3.6 명령: `/new /project /rules /report /timeout /commit /clarify /careful /status /open /exit /stop /p`.
- F3.7 화살표 키 raw 입력을 직접 해석하고 대체 키(j/k, 숫자, Tab)를 둔다. `harness keytest`로 진단한다.

### F4. 알아서 끝까지 하기
- F4.1 시작 전에는 핵심 결정만 질문한다. 새 프로젝트면 "결과물을 어떻게 쓰실 건가요?"를 반드시 묻고, 사람이 쓰는 프로그램이면 웹 화면을 1순위로 추천한다. 이 질문도 결정 카드라서 타이머가 끝나면 진행한다.
- F4.2 설치된 언어·브라우저·도구를 감지해 추천과 지시에 반영한다.
- F4.3 완료 검사: 한국어 보고, 실행 방법, 실제로 실행해 봤는지, 보류 항목. 부족하면 같은 대화로 보완 지시(최대 2번).
- F4.4 보고 끝의 글 질문("~할까요?")을 결정 카드로 바꿔 이어서 진행한다.
- F4.5 에이전트에게 다음 단계를 글로 제안하지 말고 질문 도구로 물으라고 지시한다.

### F5. 개발 파이프라인 (`/p 요청`)
- F5.1 기본 단계: 요구사항 → 설계 → 명세 → 구현 → 검증 → 커밋(허용 시).
- F5.2 단계마다 새 대화, 문서 파일로 인계. 하네스가 문서가 새로 쓰였는지 확인한다.
- F5.3 검증은 인수 기준별로 "판정: 통과/실패"를 쓰게 하고 하네스가 직접 읽는다. 실패 시 수정 → 재검증 최대 2번.
- F5.4 `pipelines/*.yaml`로 단계 추가·삭제, 단계별 모델 지정.

### F6. 맥락과 학습
- F6.1 새 대화에 그 프로젝트의 이전 작업 기록과 답 없이 취소된 요청을 넣는다.
- F6.2 사용자 지적을 규칙으로 저장한다. 자동 저장은 그 프로젝트에만, 전체 적용은 사람 승인.
- F6.3 `/rules`와 대시보드에서 규칙을 보고 고치고 지운다.

### F7. 웹 화면 확인 `harness check-web`
- F7.1 실제 마우스 클릭(가려진 요소는 오류), 키 입력, `--reload`, `--size`, `--expect`(실패 시 종료 코드 3), 콘솔 오류 수집, 스크린샷.
- F7.2 기본은 이 PC 안 주소(localhost, 127.0.0.1, ::1)만 허용. 다른 주소는 외부 통신 정책을 따른다.

### F8. 운영
- F8.1 작업 큐, 동시 실행 상한, cron 배치.
- F8.2 프로젝트는 `_projects/<이름>/`, 각자 독립 Git 저장소, 커밋 기본 안 함.
- F8.3 커밋이 있는 저장소는 작업별 worktree로 격리.
- F8.4 `harness clean`: 끝난 worktree, 오래된 로그·스크린샷 정리(삭제 전 목록 확인).
- F8.5 데스크톱 알림: 결정 필요, 작업 종료.
- F8.6 보고서(`/report`)와 대시보드(결정 카드 키보드 조작, 작업 기록, 규칙).
- F8.7 코드가 바뀌면 작업이 없을 때 서버가 스스로 재시작한다.

### F9. 반드시 넣을 것
- F9.1 중단된 작업 자동 이어가기: 시간 한도, 비용 한도, 서버 재시작, 사용량 한도, 네트워크 오류. 원인별로 기다렸다가 같은 세션으로 이어 간다. 횟수·시간 상한, 보고서에 기록.
- F9.2 예약·대기 요청을 서버 큐(DB)에 저장한다.
- F9.3 릴리스 단계: 대시보드에서 diff, 결정 기록, 검증 결과를 보고 사람이 버튼으로 push와 PR 생성(`gh`). push 차단은 이 단계에서만 풀린다.
- F9.4 서버 검토: 등록한 서버(주소, 헬스 체크, 로그 명령)를 점검하는 작업 유형과 배치. 문제는 보고서와 알림으로.
- F9.5 브리지: 일반 Claude Code 대화형 세션의 AskUserQuestion·권한 확인을 훅으로 결정 엔진에 보낸다. 설치·제거 명령을 따로 두고, 전역 설정을 바꾸기 전에 반드시 사용자 확인.
- F9.6 원격 알림과 응답: Telegram 또는 Slack으로 결정 카드를 보내고 버튼으로 답한다(설정으로 켬).
- F9.7 파이프라인 사용자 정의(F5.4와 같음).
- F9.8 PC 로그인 시 자동 실행(Windows 작업 스케줄러 등록·해제 명령).

### F10. 역할 분담
- F10.1 역할(기획, 조사, 구현, 테스트, 디버거)을 `roles.yaml`에 정의한다. 역할마다 지시문, 쓸 수 있는 도구, 막을 도구, 모델, 최대 턴 수를 정한다.
- F10.2 모든 작업에 모든 역할을 돌리지 않는다. 작업 크기(작음·보통·큼)에 따라 역할 구성을 고른다. 크기는 판단 모델이 정하고, `/p`는 항상 큼으로 본다.
- F10.3 테스트 담당은 코드를 고칠 수 없는 별도 대화에서 인수 기준별로 판정한다. 구현 대화가 스스로 검사한 결과로 완료 판정하지 않는다.
- F10.4 조사 담당은 읽기 전용이다. 디버거는 테스트가 실패했을 때만 새 대화로 투입한다.
- F10.6 품질·보안 리뷰어: 코드를 고칠 수 없는 별도 대화가 바뀐 코드만 읽고 품질·보안 점검표로 지적한다. 릴리스 전에는 항상, 작은·보통 작업은 바뀐 코드가 민감한 영역(인증, 파일 경로, 셸 실행, 외부 통신, DB 쿼리, 의존성 추가)일 때만 돌린다. 중요한 지적만 구현 담당이 한 번 고치고, 사소한 지적은 보고서에만 남긴다. 고위험 보안 지적은 릴리스를 사람 승인으로 멈춘다.
- F10.7 릴리스 정리 담당: 릴리스 화면에 보여 줄 변경 요약, PR 본문 초안, 사람이 확인할 항목을 읽기 전용으로 정리한다.
- F10.8 웹 프로젝트의 테스트 담당은 `check-web`으로 실제 클릭·스크린샷·콘솔 오류를 확인한다. 작업 끝에는 사용자 지적을 프로젝트 규칙 후보로 뽑는 짧은 마무리 단계를 둔다(별도 역할 아님).
- F10.9 역할 배정과 순서는 하네스 코드가 규칙으로 정한다. 모델에게 총괄 관리를 맡기지 않는다.
- F10.5 1~2시간 무인 시나리오에서 같은 요청을 단일 구성과 역할 분담 구성으로 돌려 비용·시간·검증 통과율을 비교하고 보고한다.

## 5. 비기능 요구사항

| ID | 요구 | 기준 |
|---|---|---|
| N1 | 무중단 | 1~2시간 무인 시나리오에서 일부러 낸 중단 3종 이상을 스스로 이어 감 |
| N2 | 최신 코드 보장 | 서버가 코드 버전을 감시하고, 클라이언트가 매 요청마다 버전을 확인 |
| N3 | 경로 일관성 | 모든 경로 비교는 `normPath` 한 함수로. `C:/a`와 `C:\a`는 같다 |
| N4 | 폴더 분리 | 설치 폴더와 데이터 폴더를 별도 변수로 두고 서로 계산하지 않는다 |
| N5 | 비용 정확성 | 이어진 세션 비용은 직전 누적값과의 차이로 기록 |
| N6 | 판단 중립성 | 판단 모델은 빈 중립 폴더, `settingSources: []`, 도구 없음, 메모리 없음 |
| N7 | 언어 일관성 | 언어 우선순위: 사용자 명시 > 프로젝트 설정 > 기본(한국어). 검사기와 판단 모델이 같은 값을 쓴다 |
| N8 | 범위 준수 | 프로젝트 규칙은 그 프로젝트에만. 전역 승격은 사람 승인 |
| N9 | 자기 보호 | 프로젝트 에이전트는 하네스 코드·정책을 사람 승인 없이 못 고친다 |
| N10 | Windows 호환 | 파일 원자적 쓰기, EBUSY 재시도, 화살표 키 대체 입력 |
| N11 | 사용량 한도 | 한도 도달은 실패가 아니라 "재설정 시각까지 대기 후 이어가기" |
| N12 | 장시간 검증 | 짧은 시험만으로 완료 판정하지 않는다. 1~2시간 무인 시나리오 필수 |
| N13 | 보안 | 서버는 127.0.0.1에만 열고, 요청마다 로컬 토큰과 Origin을 검사 |

## 6. 완료 기준

1. 첫 요청 하나로 웹 화면 생성, 브라우저 확인, 한국어 보고까지 끝나고 중간에 사용자가 되물을 일이 없다.
2. 1~2시간 무인 시나리오에서 중단이 생겨도 스스로 이어 가고, 보고서에 사람이 확인할 항목이 정리된다.
3. `docs/`에 요구사항·설계·명세·보안 정책·사용 설명서가 최신 상태로 있다.
4. 최종 커밋 push는 사용자가 한다.

## 7. 범위 밖

- 다중 사용자 인터넷 서비스, 계정·과금.
- 하네스의 자동 배포·자동 push.
- Claude 이외 모델 지원.
